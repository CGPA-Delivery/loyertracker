## Principes

* **Clarté** : un écran de gestion locative doit rester lisible même en forte densité de données
  (tableaux de paiements, échéances, garanties).
* **Cohérence** : un même statut (ex. `LOYER_EN_RETARD`, `DELIVERED`) porte toujours la même
  couleur sémantique, quel que soit l'écran.
* **Sobriété** : pas de décoration sans fonction ; le produit reste un outil de gestion, pas une
  vitrine.
* **Orientation gestion locative** : les composants transverses (statut, montant, historique) sont
  pensés pour ce domaine avant d'être génériques.
* **Prévention des erreurs financières** : toute action irréversible sur un montant, un paiement ou
  une garantie exige une confirmation explicite (patron déjà en place : formulaires bailleur,
  étendu par `lt-confirm-dialog`).
* **Lisibilité des montants** : les montants multi-devises (EUR/USD/CDF, `MoneyFormatPipe` déjà en
  Production) restent le patron de référence pour tout composant `lt-money`.
* **Traçabilité** : toute action métier sensible reste visible dans le journal d'audit existant
  (US-62) — le Design System ne doit rien masquer qui y était visible.
* **Accessibilité** : cible WCAG 2.2 AA (voir §Accessibilité).
* **Responsive** : mobile atteignable pour toute tâche critique, sans perte d'information
  financière (voir §Responsive Rules).
* **Feedback immédiat** : toute action déclenche un retour visible (message de statut, toast),
  patron déjà en place (`role="status" aria-live="polite"`).
* **Continuité Angular–Keycloak** : les écrans d'authentification (login, mot de passe oublié,
  erreurs) partagent la même identité visuelle que l'application (voir `ADR-UI-001`
  §Isolation entre Angular et Keycloak).

## Atomic Design

| Niveau | Définition pour LoyerTracker | Exemples |
|---|---|---|
| Primitives | Tokens seuls, aucun rendu propre | couleur, espacement, typographie |
| Composants | Unité fonctionnelle unique | bouton, champ texte, badge de statut |
| Patterns | Composition de composants avec une règle métier | `lt-data-table` (table + filtre + état vide), `lt-confirm-dialog` (dialogue + focus-trap) |
| Templates | Structure de page réutilisable | en-tête de page + section transverse (patron déjà en place : dashboards bailleur/gestionnaire) |
| Pages | Écran final assemblé | dashboard Bailleur, dashboard Gestionnaire |

Règle de composition : un pattern ne référence que des composants déjà documentés ici ; un
composant applicatif métier (ex. `PaiementsBienComponent`) compose des patterns, jamais l'inverse.
Règle de promotion : un composant utilisé de façon identique dans ≥ 2 écrans devient candidat à la
promotion en composant `lt-*` documenté (cf. §Component Rules).

## Responsive Rules

* Stratégie retenue : **desktop-first pragmatique pour les écrans de gestion dense** (tableaux de
  paiements, échéances, garanties), avec adaptation mobile obligatoire pour toute tâche critique —
  cf. mission §19.
* Ne jamais masquer une information financière critique sur mobile (montant, statut de paiement).
  Un tableau peut être transformé, scrollé horizontalement ou résumé selon le contexte métier —
  jamais remplacé systématiquement par des cartes sans analyse au cas par cas.
* Éviter les interactions uniquement au survol (`:hover` seul) — toujours doubler d'un focus/tap
  accessible, patron déjà respecté (`:focus-visible` global).
* Touch targets suffisants (cible ≥ 44×44px, à vérifier composant par composant lors du mapping
  PrimeNG).
* Formulaires en une colonne sur petit écran — patron déjà en place (`flex-direction: column`
  sous 640px).
* Drawers et dialogues adaptés au viewport — nouveau patron à documenter avec `lt-detail-drawer`
  et `lt-confirm-dialog` (premier modal du produit, cf. `phase-02-ui-mockups.md` §6).

## Dark Mode

Mode sombre = **cible initiale et actuelle** (mono-thème de fait aujourd'hui, `body` fixe un fond
sombre). Ce DSG **formalise** le mode sombre comme le mode par défaut du premier lot, sans
introduire de bascule automatique non maîtrisée (`color-scheme: light dark` du navigateur n'est
**pas** un mécanisme de bascule piloté — à corriger ou assumer explicitement lors du Lot 1).

## Light Mode

**Hors périmètre du premier lot**, sauf décision explicite ultérieure du Product Owner. Si
introduit, le mode clair devra utiliser les mêmes tokens sémantiques (`--lt-*`) avec des valeurs
alternatives, jamais un système de couleurs parallèle. Décision à tracer par DDS dédiée le cas
échéant.

## Accessibilité

* **Cible : WCAG 2.2 niveau AA** (mission §18).
* Patrons déjà en place à conserver : `:focus-visible` (anneau `3px solid #38bdf8`), skip-link,
  `aria-live="polite"` sur les messages de statut, `prefers-reduced-motion`.
* Points nouveaux à couvrir dès l'introduction de PrimeNG : navigation clavier et ordre de
  tabulation dans les composants complexes (table, dropdown, date picker), labels associés à
  chaque champ, annonces `aria-live` pour les toasts, gestion des erreurs de formulaire annoncées,
  touch targets, zoom 200 %, structure sémantique des tableaux, focus-trap et restitution du focus
  pour tout dialogue (**premier modal du produit**, aucun précédent — cf.
  `phase-02-ui-mockups.md` §6, candidat DDS déjà identifié).
* Toute incompatibilité connue d'un composant PrimeNG doit être documentée dans le mapping
  ci-dessous avec sa compensation, ou le composant est exclu du périmètre.
* Keycloak : le thème personnalisé doit conserver au minimum le niveau d'accessibilité du thème
  Keycloak par défaut (labels, contrastes, navigation clavier du formulaire de login).

## Component Rules

* **Création** : un composant `lt-*` n'est créé qu'après confirmation d'un besoin réel dans ≥ 2
  écrans, ou pour un besoin de sécurité/accessibilité identifié (ex. focus-trap du modal).
* **Réutilisation** : toujours préférer un composant `lt-*` existant à une nouvelle implémentation
  ad hoc dans un écran.
* **Composition** : un composant `lt-*` peut composer plusieurs composants PrimeNG, jamais
  l'inverse (un composant PrimeNG ne compose pas un `lt-*`).
* **Ownership** : Design Architect (Claude Code, sous-agent CGPA désigné le 2026-07-30) + Frontend Architect (Claude Code, sous-agent CGPA désigné le 2026-07-31).
* **API** : chaque composant `lt-*` documente ses `@Input`/`@Output` dans ce DSG avant tout usage
  applicatif.
* **Tests** : tout composant `lt-*` exige un test unitaire et, s'il porte une interaction clavier
  (dialogue, dropdown), un test d'accessibilité dédié.
* **Deprecation** : voir §Gouvernance.
* **Compatibilité** : tout changement d'API d'un composant `lt-*` est versionné et documenté ici.

## Naming Convention

* Tokens : `--lt-<catégorie>-<rôle>` (ex. `--lt-color-primary`).
* Composants : sélecteur `lt-<nom-kebab-case>` (ex. `lt-data-table`).
* Fichiers : `<nom-kebab-case>.component.ts` (convention déjà en place dans le dépôt, conservée).
* Sélecteurs de test : à définir au Lot 2 (aucune convention `data-testid` n'existe actuellement
  dans le code — dette à combler si des tests end-to-end sont introduits, hors périmètre actuel).
* Événements analytics : hors périmètre (aucun outil d'analytics n'est en place dans le produit).
* Classes utilitaires internes limitées : préfixe `lt-u-` (ex. `lt-u-truncate`), toute nouvelle
  classe utilitaire doit être ajoutée à cette liste avant usage — jamais un système utilitaire
  complet façon Tailwind (cf. `DDS-LT-001`).
