### Bailleur — objectifs, tâches, irritants

* **Objectifs** : garder une vue fiable de son patrimoine (encaissements, retards, garanties,
  honoraires dus) sans dépendre d'un tiers ; déléguer une partie de la gestion sans perdre le
  contrôle ni la traçabilité.
* **Tâches principales** (déduites des écrans réels) : créer/gérer patrimoines-biens-baux ;
  pointer les paiements ; suivre les garanties ; valider les honoraires ; consulter les alertes et
  le journal d'audit ; gérer les affectations de gestionnaires.
* **Irritants observés dans le code** (pas déclaratifs — constatés) :
  * aucun état de chargement uniforme (chaque composant affiche son propre texte brut
    « Chargement… » ou rien) ;
  * aucun état « accès refusé » côté client : un 403 serveur n'est traduit par aucun composant
    dédié, seulement par l'absence de données ou un message générique selon l'écran ;
  * aucune pagination ni filtre sur les listes transversales (Alertes, Audit) — accepté comme
    limite volontaire à ce jour (`phase-02-design-system.md` §5), mais irritant potentiel si le
    volume de données augmente ;
  * pas de page « Mon profil » équivalente pour le Gestionnaire, alors qu'elle existe pour le
    Bailleur — asymétrie d'expérience entre les deux rôles.

### Gestionnaire — objectifs, tâches, irritants

* **Objectifs** : gérer efficacement le périmètre qui lui est délégué, sans risque de confondre
  les biens de bailleurs différents s'il en gère plusieurs.
* **Tâches principales** : consulter les biens affectés ; créer/gérer les baux ; pointer les
  paiements ; consulter les garanties et honoraires (lecture seule pour la validation) ; consulter
  ses alertes.
* **Irritants observés** : mêmes irritants transverses que le Bailleur (chargement, accès refusé,
  absence de filtre) ; risque spécifique de confusion multi-bailleur déjà identifié en
  `phase-02-user-journeys.md` §1.2, aucun repère visuel de tenant courant dans l'interface actuelle
  (le nom du bailleur géré n'apparaît pas systématiquement dans le dashboard Gestionnaire — à
  vérifier précisément lors du mapping composants, hypothèse à confirmer).

| Besoin de confirmation | Confirmé par le domaine (financier) et par le premier modal identifié (`lt-confirm-dialog`, désinscription notifications) |

### Parcours critiques (produit, au-delà d'US-125)

* Pointage d'un paiement (Bailleur/Gestionnaire) — action financière fréquente, déjà en Production.
* Consultation/validation des honoraires (Bailleur) — impact direct sur la rémunération du
  Gestionnaire, sensibilité élevée.
* Vérification publique d'une quittance (Locataire/tiers, non authentifié, `/verify/receipt/:id`)
  — seul point de contact UI du Locataire, criticité de confiance (preuve légale potentielle).
* Gestion des préférences/historique de notifications (Bailleur/Gestionnaire, US-125) — déjà
  couvert en détail §Identification à §Traçabilité ci-dessus.

### Erreurs à prévenir

* Confirmer une action financière irréversible sans étape de confirmation explicite.
* Laisser un Gestionnaire multi-bailleur agir sur le mauvais tenant sans repère visuel suffisant.
* Masquer une information financière critique sur mobile au nom de la simplification visuelle.
* Introduire un composant PrimeNG dont l'état d'erreur/vide/chargement diffère du reste du produit
  (incohérence déjà en germe : chaque composant existant gère ces états à sa façon aujourd'hui).

### Besoins d'accessibilité

Repris de `DSG-001.md` §Accessibilité (WCAG 2.2 AA) : focus visible, navigation clavier complète y
compris pour les futurs composants PrimeNG (table, dialogue, dropdown), labels de formulaire,
annonces `aria-live` pour les futurs toasts, structure sémantique des tableaux denses, zoom 200 %,
`prefers-reduced-motion` (déjà respecté). Point neuf à couvrir explicitement : focus-trap et
restitution du focus du premier dialogue modal du produit (`lt-confirm-dialog`).

### Hypothèses à valider (explicitement non prouvées)

* Le volume réel de notifications/alertes par utilisateur reste faible (justifierait l'absence de
  filtre/pagination) — **non mesuré**.
* La connectivité mobile des utilisateurs RDC est variable — **non mesurée**, aucune télémétrie.
* Le Gestionnaire gère fréquemment plusieurs bailleurs en parallèle — **plausible par construction
  du modèle de données** (`Affectation` par bailleur), non confirmé par un usage réel observé.
* Le mode sombre actuel est acceptable pour l'ensemble des utilisateurs cibles — **jamais demandé
  ni testé**, simple conséquence d'un choix de développement initial.
